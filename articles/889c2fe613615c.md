## 概要

今回は Cloudflare R2 にオブジェクトが追加されたタイミングで、Queues へイベントを送り、Consumer Worker で非同期処理する構成を試してみたいと思います。

構成としてはかなりシンプルです。

```plain text
R2
 ↓ Event Notification
Queues
 ↓
Consumer Worker
```

R2 へのアップロード処理自体はそのまま終了させて、画像処理や DB 更新などの少し重い処理を Queue の先で実行したいケースを想定しています。

実際に試してみると設定自体はそこまで難しくなかったのですが、ローカル開発や Queues 特有の挙動でいくつかハマったので、そのあたりも含めてまとめます。

## R2 バケットを作成

まず R2 バケットを作成します。

```bash
bunx wrangler r2 bucket create <BUCKET_NAME>
```

対話形式で binding を追加するか聞かれるので、そのまま追加しました。

最終的に `wrangler.jsonc` には以下のような設定が入ります。

```json
{
  "r2_buckets": [
    {
      "bucket_name": "<BUCKET_NAME>",
      "binding": "R2"
    }
  ]
}
```

ちなみに `--location` でヨーロッパを指定する場合は `eu` ではなく `weur` / `eeur` になります。

`--jurisdiction eu` とは意味が違い、`location` は配置場所のヒント、`jurisdiction` はデータを保存する法域の制約なので注意が必要そうです。

## Queue を作成

次に Queue を作成します。

```bash
bunx wrangler queues create <QUEUE_NAME>
```

R2 とは違い、こちらは設定ファイルへ自動追記するか聞かれず、producer / consumer それぞれの設定例が表示されるだけでした。

今回は R2 が Queue へイベントを送ってくれるため、Worker は producer にはなりません。

必要なのは consumer 側だけです。

```json
{
  "queues": {
    "consumers": [
      {
        "queue": "<QUEUE_NAME>",
        "max_batch_size": 10,
        "max_batch_timeout": 1
      }
    ]
  }
}
```

`max_batch_timeout` については後ほど触れます。

## R2 から Queue へ Event Notification を設定

続いて R2 と Queue を繋ぎます。

```bash
bunx wrangler r2 bucket notification create <BUCKET_NAME> \
  --event-type object-create \
  --queue <QUEUE_NAME>
```

これで R2 にオブジェクトが作成されると Queue へイベントが送られるようになります。

`object-create` は実際には以下が対象になります。

- `PutObject`

- `CopyObject`

- `CompleteMultipartUpload`

つまり単純な PUT だけではなく、コピーや Multipart Upload 完了時にも通知されます。

prefix / suffix による絞り込みも可能ですが、正規表現までは使えないため、複雑な条件が必要なら Consumer 側で判定するのが良さそうです。

## Consumer Worker を実装

Consumer 側は `queue()` を実装するだけです。

まずはどんなデータが来るのか確認したかったので、そのままログへ出してみました。

```typescript
export default {
  async queue(batch: MessageBatch, env: CloudflareBindings) {
    for (const message of batch.messages) {
      console.log(JSON.stringify(message.body));
    }
  },
} satisfies ExportedHandler<CloudflareBindings>;
```

R2 へファイルをアップロードします。

```bash
bunx wrangler r2 object put \
  <BUCKET_NAME>/sample.txt \
  --file=sample.txt \
  --remote
```

Consumer 側には以下のようなデータが届きました。

```json
{
  "account": "xxxxxxxx",
  "action": "PutObject",
  "bucket": "<BUCKET_NAME>",
  "object": {
    "key": "sample.txt",
    "size": 123,
    "eTag": "..."
  },
  "eventTime": "..."
}
```

キー、サイズ、eTag、イベント発生日時などは取得できます。

一方で `content-type` やカスタムメタデータは含まれていませんでした。

画像ファイルを以下のように `content-type` を明示してアップロードしてみます。

```bash
bunx wrangler r2 object put \
  <BUCKET_NAME>/sample.jpeg \
  --file=sample.jpeg \
  --content-type=image/jpeg \
  --remote
```

この場合も通知のペイロードに `content-type` は含まれませんでした。

そのため Consumer 側でファイル種別や metadata が必要な場合は、`object.key` を使って R2 からオブジェクトを取り直す必要がありそうです。

## max_batch_timeout で約 5 秒待たされる

最初に試したとき、R2 に PUT してから Consumer が実行されるまで約 6 秒ほどかかっていました。

```plain text
R2 PUT
  ↓
Queue
  ↓
Consumer 実行
```

思ったより遅いなと思って調べたところ、Queues の Consumer には `max_batch_timeout` があり、デフォルトが 5 秒になっています。

そこで以下のように 1 秒へ変更してみます。

```json
{
  "queues": {
    "consumers": [
      {
        "queue": "<QUEUE_NAME>",
        "max_batch_size": 10,
        "max_batch_timeout": 1
      }
    ]
  }
}
```

変更後はかなり早く Consumer が実行されるようになりました。

リアルタイム性を優先するなら小さく、まとめて処理して Worker の呼び出し回数を減らしたい場合は大きくする、という使い分けになりそうです。

## ローカル開発で少しハマった

ここが今回一番分かりにくかったところです。

R2 自体はローカル環境を使うことも、本物の R2 を remote binding として使うこともできます。

ただし Queues の Consumer については、「リモート Queue に入ったメッセージをローカルで動いている Consumer Worker へ push する」という使い方はできません。

Queues 自体のローカルシミュレーションはできるので、以下のような構成なら確認できます。

```plain text
Local Producer
 ↓
Local Queue
 ↓
Local Consumer
```

一方で R2 Event Notification は Cloudflare 側の R2 で発火するため、今回のような構成を一通り確認したい場合は Consumer Worker を一度 deploy して試すのが分かりやすそうです。

このあたりは、R2 binding に `remote: true` があるので Queue も同じようにできそうに見えるのですが、producer と consumer では挙動が違うため注意が必要でした。

## wrangler deploy が一部だけ成功するケース

もうひとつ少し怖かったのが `wrangler deploy` です。

Consumer 設定に問題がある状態で deploy すると、Worker コード自体のアップロードは成功しているものの、Queue Consumer Trigger の設定だけ失敗するケースがありました。

```plain text
Worker コード     → 更新済み
HTTP 側の Trigger → 更新済み
Queue Consumer    → 更新失敗
```

つまり `wrangler deploy` 全体がひとつのトランザクションとして動いているわけではなく、途中まで反映された状態になることがあります。

deploy が失敗したから「何も変更されていない」と思い込まないほうが良さそうです。

Cloudflare Dashboard や deploy 時のログを見て、Consumer まで正しく紐づいているか確認しておくと安心です。

## まとめ

今回は以下の構成を実際に試してみました。

```plain text
R2 → Event Notification → Queues → Consumer Worker
```

設定自体はかなりシンプルで、R2 への書き込み処理と、その後の重い処理を分離したい場合にはかなり使いやすそうです。

特に今回試して気になったのは以下でした。

- `max_batch_timeout` のデフォルトが 5 秒なので、少量のメッセージでは少し待つ

- R2 Event Notification には `content-type` などが含まれない

- ローカルの Consumer でリモート Queue のイベントをそのまま受けることはできない

- `wrangler deploy` が部分的に成功するケースがある

画像アップロード後の変換処理や、R2 へのファイル保存をトリガーに DB を更新するような処理では使いやすそうなので、今後実際のサービスでも使ってみたいと思います。
