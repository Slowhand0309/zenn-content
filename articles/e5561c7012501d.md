# はじめに

- この記事は、複数のモバイルアプリの広告収益（AdMob）を、サーバー側の定期実行スクリプトで自動収集するための手順をまとめたものです。

- **個人のGoogleアカウント**を使ったGCPプロジェクトで、OAuthクライアントを作成し、AdMob APIから実際のレポートデータを取得するところまでを通して説明します。

- 実際に進める中で詰まった、次のようなポイントもまとめます。
  - サービスアカウントではなく、ユーザーの同意を伴うOAuthが必要

  - 個人アカウントではUser Typeが`External`になる

  - リモートサーバー上でループバックリダイレクトを使う場合はSSHポートフォワーディングが必要

  - AdMobでは「1アプリ = 1 App ID」とは限らない

## 大まかな流れ

1. GCPプロジェクトでAdMob APIを有効化する

1. OAuth同意画面を設定する

1. OAuthクライアント（デスクトップアプリ）を作成する

1. ブラウザでの同意フローから初回のリフレッシュトークンを取得する

1. リフレッシュトークンからアクセストークンを更新するクライアントを実装する

1. `accounts.list`でAdMobアカウント情報を取得する

1. `networkReport:generate`で実際の広告収益データを取得する

## ゴール

個人のGoogleアカウント・個人のAdMobパブリッシャーアカウントでも、初回認証後はサーバーの定期実行からAdMobの広告収益データを自動収集できる状態を作ります。

# 環境構築や準備

- Node.js 22以上
  - 今回は組み込みモジュールのみで完結させ、追加パッケージは使いません

- 個人のGoogleアカウント
  - Google Workspaceなどの組織アカウントではないもの

- 既存のAdMobパブリッシャーアカウント
  - 広告収益が発生しているアプリがあること

- GCPプロジェクト
  - 新規でも既存プロジェクトの流用でもOK

# 実装

## **1. GCPプロジェクトでAdMob APIを有効化する**

Google Cloud Consoleで対象プロジェクトを開き、**「APIとサービス」→「ライブラリ」**から「AdMob API」を検索して有効化します。

有効化後、AdMob APIの画面でステータスが**「有効」**になっていればOKです。

![](/images/e5561c7012501d/3c5a252da4fa8015ab72f110de64747b.png)

## **2. OAuth同意画面を設定する**

「APIとサービス」→「OAuth同意画面」からGoogle Auth Platformの設定を開始します。

![](/images/e5561c7012501d/3c5a252da4fa80dcae80ee1e8b909bac.png)

初回の場合は「Google Auth Platform はまだ構成されていません」と表示されるため、**「開始」**を押して設定を進めます。

![](/images/e5561c7012501d/3c5a252da4fa8008b94feee74685b458.png)

### **2-1. アプリ情報を入力する**

- アプリ名

- ユーザーサポートメール

を設定します。

アプリ名は、このOAuth認証を識別できる分かりやすい名前で問題ありません。

![](/images/e5561c7012501d/3c5a252da4fa80ce979acc3453dd7f9b.png)

### **2-2. 個人アカウントでは「内部（Internal）」を選べない**

個人のGoogleアカウントで作成したGCPプロジェクトには、Google Cloud Organization（Google Workspaceなどの組織）が存在しません。

そのため、User Typeでは**「内部」ではなく「外部（External）」を選択**します。

![](/images/e5561c7012501d/3c5a252da4fa8088ac02c3084ae7d562.png)

Googleの説明でも、InternalはGoogle Cloud Organizationに関連付けられたプロジェクトで利用するものとされています。

「Externalにすると審査が必要なのでは？」と少し身構えますが、自分だけで利用する用途なら、公開ステータスを**「テスト」**のままにして、自分のGoogleアカウントをテストユーザーへ追加する形で利用できます。

### **2-3. テストユーザーを追加する**

Google Auth Platformの**「対象」**画面を開き、テストユーザーの「Add users」から、実際にAdMobを利用している自分のGoogleアカウントを追加します。

![](/images/e5561c7012501d/3c5a252da4fa801183aec3a2a14a62fd.png)

テスト状態では、ここに登録したユーザーのみOAuth認証を行えます。

## **3. OAuthクライアント（デスクトップアプリ）を作成する**

Google Auth Platformの**「クライアント」**からOAuthクライアントIDを作成します。

- アプリケーションの種類：**デスクトップアプリ**

- 名前：用途が分かる任意の名前

![](/images/e5561c7012501d/3c5a252da4fa80d185c5e60d19a8ac0c.png)

作成後に発行される以下の値を、この後のスクリプトで利用します。

- Client ID

- Client Secret

> 💡 **Webアプリケーションではなく「デスクトップアプリ」を選ぶのがポイントです。**

デスクトップアプリタイプでは、リダイレクトURIとして`http://127.0.0.1:<任意のポート>/...`のようなループバックアドレスを利用できます。

これにより、スクリプト自身が一時的なHTTPサーバーを立ててOAuthのリダイレクトを直接受け取れます。人間が行う作業は、表示されたURLをブラウザで開いて同意するだけです。

## **4. 初回のリフレッシュトークンを取得するスクリプトを実装する**

今回利用するスコープは次の2つです。

- `https://www.googleapis.com/auth/admob.readonly`
  - AdMobアカウント情報の読み取り

- `https://www.googleapis.com/auth/admob.report`
  - 収益・パフォーマンスレポートの取得

```javascript
import { createServer } from "node:http";

const authUrl = new URL("https://accounts.google.com/o/oauth2/v2/auth");
authUrl.searchParams.set("client_id", clientId);
authUrl.searchParams.set("redirect_uri", `http://127.0.0.1:${port}/oauth2callback`);
authUrl.searchParams.set("response_type", "code");
authUrl.searchParams.set(
  "scope",
  "https://www.googleapis.com/auth/admob.readonly https://www.googleapis.com/auth/admob.report",
);
authUrl.searchParams.set("access_type", "offline");
authUrl.searchParams.set("prompt", "consent");
authUrl.searchParams.set("state", state);

console.log(`このURLをブラウザで開いてください: ${authUrl}`);

const server = createServer((req, res) => {
  const url = new URL(req.url, `http://127.0.0.1:${port}`);
  const code = url.searchParams.get("code");

  res.end("認可を受け取りました。このタブは閉じて構いません。");
  server.close();

  // ここでcodeをアクセストークン・リフレッシュトークンに交換する
});

server.listen(port, "127.0.0.1");
```

特に重要なのが次の2つです。

- `access_type=offline`
  - リフレッシュトークンを取得するために必要

- `prompt=consent`
  - 以前に同意済みのアカウントでも、再度同意画面を出してリフレッシュトークンを取得しやすくする

### **認証情報は標準出力へ出さない**

取得した以下の値は、標準出力へ表示せず、直接ファイルへ保存する設計にしました。

- Client ID

- Client Secret

- Refresh Token

保存先ファイルのパーミッションは`600`にします。

> 🔐 コーディングエージェントを利用している場合、秘密情報を標準出力へ表示すると、対話ログやツール実行結果を経由してエージェント側のコンテキストへ入る可能性があります。**「ファイルへ書き込むだけで、一度も表示しない」設計**にしておくと安心です。

## **5. サーバーとブラウザが別端末の場合の注意（SSHポートフォワーディング）**

ここが今回かなりハマったポイントでした。

作業用サーバーへSSHでログインしてスクリプトを実行し、OAuthの同意画面だけ手元のPCのブラウザで開く場合、そのままではループバックリダイレクトが届きません。

`127.0.0.1`は「その通信を行っている端末自身」を意味するためです。

- スクリプト：リモートサーバーの`127.0.0.1:<port>`で待ち受ける

- ブラウザ：手元PCの`127.0.0.1:<port>`へアクセスする

この2つは別物なので、ブラウザ側では「接続を拒否されました」となります。

### **解決方法：SSHローカルポートフォワーディング**

ブラウザを開く**手元のPC側**で、次のSSH接続を張ったままにします。

```bash
ssh -L <port>:127.0.0.1:<port> <サーバーのSSHユーザー>@<サーバーのホスト名/IP>
```

その状態でOAuthの認可URLを開くと、手元PCの`127.0.0.1:<port>`へのアクセスがSSHトンネル経由でサーバー側の同じポートへ転送されます。

OAuth側のリダイレクトURI設定を変更する必要はありません。

## **6. リフレッシュトークンからアクセストークンを取得するクライアントを実装する**

初回認証でリフレッシュトークンを取得できたら、それ以降はサーバー側だけでアクセストークンを更新できます。

```javascript
async function fetchAccessToken({ clientId, clientSecret, refreshToken }) {
  const res = await fetch("https://oauth2.googleapis.com/token", {
    method: "POST",
    headers: { "content-type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      client_id: clientId,
      client_secret: clientSecret,
      refresh_token: refreshToken,
      grant_type: "refresh_token",
    }),
  });

  const json = await res.json();
  return {
    accessToken: json.access_token,
    expiresIn: json.expires_in,
  };
}
```

アクセストークンには有効期限があるため、期限の60秒程度手前でキャッシュを失効させ、必要なタイミングだけリフレッシュする実装にしました。

## **7. ****`accounts.list`****でpublisherId・タイムゾーン・通貨を確認する**

アクセストークンを取得できたら、まずAdMobアカウント情報を取得します。

```plain text
GET https://admob.googleapis.com/v1/accounts
Authorization: Bearer <access_token>
```

レスポンスから主に次の値を確認できます。

- `publisherId`
  - `pub-`から始まるAdMobパブリッシャーID

- `reportingTimeZone`
  - レポートの日付集計に使われるタイムゾーン

- `currencyCode`
  - レポートで利用される通貨

日次集計を行う場合は、サーバーのタイムゾーンではなく**`reportingTimeZone`****を基準にする**のが安全です。

## **8. ****`networkReport:generate`****で実データを取得する**

続いて広告収益・インプレッションなどの実データを取得します。

```plain text
POST https://admob.googleapis.com/v1/accounts/{publisherId}/networkReport:generate
```

リクエスト例です。

```json
{
  "reportSpec": {
    "dateRange": {
      "startDate": { "year": 2026, "month": 8, "day": 16 },
      "endDate": { "year": 2026, "month": 8, "day": 23 }
    },
    "dimensions": ["DATE", "APP"],
    "metrics": ["AD_REQUESTS", "IMPRESSIONS", "CLICKS", "ESTIMATED_EARNINGS"]
  }
}
```

レスポンスは単一オブジェクトではなく、**`header`**** / ****`row`**** / ****`footer`****が混在したJSON配列**で返ります。

実データとして利用する場合は`row`を持つ要素だけを取り出し、`dimensionValues`と`metricValues`から値を取得します。

```json
{
  "row": {
    "dimensionValues": {
      "DATE": { "value": "20260816" },
      "APP": {
        "value": "ca-app-pub-XXXXXXXXXXXXXXXX~YYYYYYYYYY",
        "displayLabel": "アプリの表示名"
      }
    },
    "metricValues": {
      "AD_REQUESTS": { "integerValue": "16" },
      "IMPRESSIONS": { "integerValue": "9" },
      "CLICKS": { "integerValue": "1" },
      "ESTIMATED_EARNINGS": { "microsValue": "19967285" }
    }
  }
}
```

# バッドノウハウ

## **`ESTIMATED_EARNINGS`****が100万分の1単位（micros）で返ってくる**

### **エラーの詳細**

APIエラーにはなりませんが、そのまま保存すると収益が実際の100万倍の値になってしまいます。

### **原因**

`metricValues.ESTIMATED_EARNINGS`は`microsValue`で返ります。

例えば次の値の場合、実際の収益は約19.97通貨単位です。

```plain text
19967285 / 1_000_000 = 19.967285
```

他の指標は`integerValue`で返るため、同じ処理でまとめて扱うと見落としやすいポイントです。

### **解決方法**

- `microsValue`を持つ指標だけ`1_000_000`で割る

- 保存処理でも「整数値の指標」と「microsの指標」を明示的に分ける

- DB側のカラム名や変換処理から単位が分かるようにしておく

## **1つのアプリに複数のAdMob App ID（Android/iOS別）が存在する**

### **エラーの詳細**

これはエラーではなく、設計時の思い込みによる見落としでした。

最初は「1アプリ = 1つのAdMob App ID」という前提で、`APP`ディメンションのフィルタを組もうとしていました。

### **原因**

AdMobではAndroid/iOSなど、プラットフォームごとに別のApp IDが発行されます。

さらに実データを確認すると、過去のリブランドやアプリ名変更によって使われなくなった旧App IDが、同じAdMobアカウント内に残っているケースもありました。

RevenueCatやGA4などで「1プロダクト = 1プロジェクト/プロパティ」の感覚に慣れていると、この違いを見落としやすいです。

### **解決方法**

- 実装前に、APPの絞り込みをせず一度レポートを取得する

- 実際に存在するApp IDと`displayLabel`を全部洗い出す

- 「1アプリ → 複数App ID」を前提に、配列で複数IDを保持する

- 集計時には同一アプリとして合算する

- 表示名だけで判別できないApp IDは、人間がプラットフォームやアプリとの対応関係を確認する

> ✅ **推測でApp IDのマッピングを作らず、最初に絞り込みなしで実データを取得してから設計を決めるのが一番早いです。**

# まとめ

- **良かった点**
  - サービスアカウントが使えない構成でも、デスクトップアプリ向けOAuthクライアント + ループバックリダイレクトで、初回同意後は無人実行できる構成にできた

- **問題点**
  - 個人アカウントではExternalを使うこと、別端末でのループバックにはSSHトンネルが必要なことなど、実際に試すまで分かりづらい点が多かった

  - 「1アプリ = 1 App ID」という他サービスでの感覚をそのままAdMobへ持ち込むと設計を間違えやすい

- **どうしたら良いか**
  - OAuth設定だけで設計を確定せず、まずAPIを絞り込みなしで一度叩く

  - `publisherId`、タイムゾーン、App ID、表示名、収益の単位など、実際に返ってくるデータを確認してからデータモデルを決める
