# 概要

Firebase AuthenticationでログインしたクライアントからIDトークンを受け取り、Cloudflare Workers側で署名とクレームを検証する構成を実装しました。

Firebase Admin SDKのNode.js版は、特権的なサーバー環境向けのSDKです。Cloudflare Workersは`nodejs_compat`によってNode.js APIへの対応を広げていますが、すべてのnpmパッケージがそのまま動くことを保証するものではありません。

今回必要だったのはユーザー管理やトークン失効ではなく、**受け取ったFirebase IDトークンが正しいかを検証することだけ**でした。そのため、Workersを正式な対応ランタイムに含む`jose`を使い、署名とクレームを直接検証する構成にしました。

> 💡 **今回の方針**

# この構成でできること・できないこと

この構成で行うのは、IDトークンの署名と標準クレームの検証です。

- トークンがGoogleの公開鍵に対応する秘密鍵で署名されていること

- 対象のFirebaseプロジェクト向けに発行されていること

- 有効期限内であること

- Firebase UIDとして利用する`sub`が正しいこと

一方、次の処理は含まれません。

- IDトークンが発行後に失効されたかの確認

- Firebase Authentication上でユーザーが無効化・削除されていないかの確認

- Firebaseユーザーの作成・更新・削除

Firebase Admin SDKの`verifyIdToken()`も、通常の呼び出しでは失効確認を行いません。失効やユーザー状態まで確認したい場合は、追加のGoogle APIアクセスやAdmin SDKを含む別の設計が必要です。

> 🔐 この記事で「secretが不要」と書いているのは、**IDトークンの署名・クレーム検証だけを行う場合**です。Firebaseの管理APIを呼ぶ場合まで秘密情報が不要になるわけではありません。

# Firebase IDトークンで確認する項目

Firebase公式ドキュメントでは、サードパーティーのJWTライブラリで検証する場合、次の項目を確認するよう案内されています。

| 項目 | 確認内容 | 実装 |
| --- | --- | --- |
| `alg` | `RS256`であること | `jwtVerify()`の`algorithms` |
| `kid` | 公開鍵セットに対応する鍵があること | `createLocalJWKSet()` |
| `exp` | 有効期限が未来であること | `jwtVerify()` |
| `iat` | 発行時刻が未来でないこと | 存在確認＋独自チェック |
| `aud` | FirebaseプロジェクトIDと一致すること | `jwtVerify()`の`audience` |
| `iss` | `https://securetoken.google.com/{projectId}`であること | `jwtVerify()`の`issuer` |
| `sub` | 空でないFirebase UIDであること | 存在確認＋独自チェック |
| `auth_time` | 認証時刻が未来でないこと | 存在確認＋独自チェック |

`jwtVerify()`へ`issuer`と`audience`を渡すと、署名に加えて`iss`・`aud`・`exp`などを検証できます。ただし、`iat`は存在しているだけでは未来時刻を自動で拒否しないため、Firebaseの要件に合わせて明示的に確認します。

```typescript
import {
  createLocalJWKSet,
  decodeProtectedHeader,
  jwtVerify,
  type JWTPayload,
} from 'jose'

type FirebaseIdTokenPayload = JWTPayload & {
  auth_time?: number
  email?: string
  email_verified?: boolean
  firebase?: {
    sign_in_provider?: string
  }
}

const CLOCK_TOLERANCE_SEC = 30

export async function verifyFirebaseIdToken(
  token: string,
  projectId: string,
): Promise<FirebaseIdTokenPayload> {
  const header = decodeProtectedHeader(token)

  // セキュリティ上はjwtVerifyのalgorithms指定で拒否できる。
  // ここではログ・エラー分類を分かりやすくするため先に確認する。
  if (header.alg !== 'RS256') {
    throw new ApiError(
      401,
      'unauthenticated',
      `IDトークンのalgがRS256ではありません: ${header.alg ?? 'missing'}`,
    )
  }

  if (!header.kid) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンにkidがありません')
  }

  const keySet = await fetchJwks(Date.now())
  const { payload } = await jwtVerify<FirebaseIdTokenPayload>(
    token,
    createLocalJWKSet(keySet),
    {
      algorithms: ['RS256'],
      issuer: `https://securetoken.google.com/${projectId}`,
      audience: projectId,
      requiredClaims: ['exp', 'iat', 'sub', 'auth_time'],
      clockTolerance: CLOCK_TOLERANCE_SEC,
    },
  )

  const nowSec = Math.floor(Date.now() / 1000)

  if (!payload.sub) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのsubが空です')
  }

  if (payload.iat === undefined || payload.iat > nowSec + CLOCK_TOLERANCE_SEC) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのiatが不正です')
  }

  if (
    payload.auth_time === undefined ||
    payload.auth_time > nowSec + CLOCK_TOLERANCE_SEC
  ) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのauth_timeが不正です')
  }

  return payload
}
```

`decodeProtectedHeader()`で取得した値は、この時点では未検証です。エラーメッセージの分類には使えますが、認可判断には使用せず、必ず`jwtVerify()`を通した後の値を利用します。

# 公開鍵はJWK形式で取得する

Firebase公式ドキュメントが案内している公開鍵URLは、X.509証明書を返します。

```plain text
https://www.googleapis.com/robot/v1/metadata/x509/securetoken@system.gserviceaccount.com
```

`jose`の`createLocalJWKSet()`へそのまま渡したい場合は、Googleがサービスアカウントの公開鍵用に提供しているJWK形式のエンドポイントを利用できます。

```typescript
const JWKS_URL =
  'https://www.googleapis.com/service_accounts/v1/metadata/jwk/' +
  'securetoken@system.gserviceaccount.com'
```

どちらも`securetoken@system.gserviceaccount.com`の公開鍵を取得するものです。Firebase公式の説明と実装形式を混同しないよう、記事やコードでは「Firebase公式が案内するX.509公開鍵」と「実装で利用するGoogleのJWKエンドポイント」を分けて記載しておくと安全です。

# `createRemoteJWKSet`ではなく自前キャッシュを使う

`jose`には`createRemoteJWKSet()`があり、JWKSの取得・メモリキャッシュ・再取得をまとめて扱えます。現在のAPIには`reload()`やキャッシュの受け渡し機能もあるため、多くのケースではこちらで十分です。

今回は、次の理由から自分で`fetch()`し、取得済みのJWKSを`createLocalJWKSet()`へ渡す形にしました。

1. Googleのレスポンスに含まれる`Cache-Control: max-age`を、そのままキャッシュ期限へ反映したい

1. テストごとにキャッシュを確実に初期化したい

1. 公開鍵取得失敗時のHTTPステータスやログをアプリ側で統一したい

`createRemoteJWKSet()`の`cacheMaxAge`は設定できますが、レスポンスの`Cache-Control`を自動的に期限へ反映するAPIではありません。したがって、今回の自前キャッシュは必須ではなく、**キャッシュ方針をGoogleのレスポンスへ合わせるための選択**です。

```typescript
import type { JSONWebKeySet } from 'jose'

const DEFAULT_JWKS_TTL_MS = 10 * 60 * 1000

let jwksCache:
  | {
      keySet: JSONWebKeySet
      expiresAt: number
    }
  | undefined

export function clearJwksCache(): void {
  jwksCache = undefined
}

function parseMaxAgeMs(cacheControl: string | null): number | undefined {
  if (!cacheControl) return undefined

  const match = cacheControl.match(/(?:^|,)\s*max-age=(\d+)\s*(?:,|$)/i)
  if (!match) return undefined

  return Number(match[1]) * 1000
}

async function fetchJwks(now: number): Promise<JSONWebKeySet> {
  if (jwksCache && jwksCache.expiresAt > now) {
    return jwksCache.keySet
  }

  const res = await fetch(JWKS_URL)
  if (!res.ok) {
    throw new ApiError(
      503,
      'internal_error',
      'Firebase IDトークンの公開鍵を取得できませんでした',
      { status: res.status },
    )
  }

  const keySet = (await res.json()) as JSONWebKeySet
  if (!Array.isArray(keySet.keys) || keySet.keys.length === 0) {
    throw new ApiError(503, 'internal_error', '公開鍵セットが空です')
  }

  const maxAge =
    parseMaxAgeMs(res.headers.get('cache-control')) ?? DEFAULT_JWKS_TTL_MS

  jwksCache = {
    keySet,
    expiresAt: now + maxAge,
  }

  return keySet
}
```

キャッシュはモジュールスコープに置いているため、同じWorker isolateが再利用される間だけ有効です。Cloudflare Workersはisolateの再利用期間を保証していないため、永続キャッシュとしては扱えません。

ただし、小規模なAPIであれば「isolateごとの初回検証時に公開鍵を1回取得する」構成でも十分です。複数isolate間で共有したくなった段階で、Cache APIやKVを検討できます。

> ⚠️ 共有キャッシュを追加する場合も、Googleの`max-age`を超えて古い鍵を保持しないことと、未知の`kid`を受け取った際に公開鍵を再取得できることが重要です。

# テストではJWKSだけをモックする

テストでは、認証処理そのものをモックしません。

- `generateKeyPair('RS256')`でテスト用の鍵ペアを生成する

- 公開鍵をJWKへ変換し、JWKSエンドポイントのレスポンスとして返す

- 秘密鍵でテスト用IDトークンを実際に署名する

- 本番と同じ`jwtVerify()`で検証する

これにより、署名アルゴリズム・`kid`・公開鍵選択・クレーム検証を含めた経路を確認できます。

```typescript
import { exportJWK, generateKeyPair, type JSONWebKeySet } from 'jose'
import { vi } from 'vitest'

const TEST_KID = 'test-key-1'

export async function installJwksMock(): Promise<ReturnType<typeof vi.fn>> {
  const { publicKey } = await getKeys()
  const jwk = {
    ...(await exportJWK(publicKey)),
    kid: TEST_KID,
    alg: 'RS256',
    use: 'sig',
  }

  const keySet: JSONWebKeySet = { keys: [jwk] }
  const fetchMock = vi.fn(async (input: RequestInfo | URL) => {
    const url = input instanceof Request ? input.url : String(input)

    if (url === JWKS_URL) {
      return Response.json(keySet, {
        headers: {
          'cache-control': 'public, max-age=3600',
        },
      })
    }

    throw new Error(`テストが想定していない外部fetch: ${url}`)
  })

  clearJwksCache()
  vi.stubGlobal('fetch', fetchMock)
  return fetchMock
}
```

`vi.stubGlobal()`は自動では元に戻りません。`afterEach()`で`vi.unstubAllGlobals()`を呼ぶか、Vitestの`unstubGlobals: true`を設定します。JWKSキャッシュも同時に消して、テスト順序へ依存しないようにします。

```typescript
import { afterEach, vi } from 'vitest'

afterEach(() => {
  clearJwksCache()
  vi.unstubAllGlobals()
})
```

# 正常系・異常系のトークンを発行する

正常なトークンは`SignJWT`で生成します。Firebase IDトークンの要件に合わせて、`iat`と`auth_time`も設定します。

```typescript
import { SignJWT } from 'jose'

type IdTokenOptions = {
  uid?: string
  kid?: string
  issuer?: string
  audience?: string
  issuedAt?: number
  authTime?: number
  expiresAt?: number
  signWithForeignKey?: boolean
}

export async function issueIdToken(
  options: IdTokenOptions = {},
): Promise<string> {
  const nowSec = Math.floor(Date.now() / 1000)
  const keys = options.signWithForeignKey
    ? await getForeignKeys()
    : await getKeys()

  return new SignJWT({
    auth_time: options.authTime ?? nowSec,
  })
    .setProtectedHeader({
      alg: 'RS256',
      kid: options.kid ?? TEST_KID,
    })
    .setSubject(options.uid ?? 'uid-1')
    .setIssuedAt(options.issuedAt ?? nowSec)
    .setIssuer(
      options.issuer ??
        `https://securetoken.google.com/${TEST_PROJECT_ID}`,
    )
    .setAudience(options.audience ?? TEST_PROJECT_ID)
    .setExpirationTime(options.expiresAt ?? nowSec + 3600)
    .sign(keys.privateKey)
}
```

これで次の異常系を、本物の暗号処理を通して作れます。

- 期限切れの`exp`

- 未来の`iat`

- 未来の`auth_time`

- 別プロジェクトの`aud`

- 不正な`iss`

- 空の`sub`

- JWKSに存在しない`kid`

- JWKSの公開鍵とは異なる秘密鍵で署名したトークン

「JWKSに存在しない`kid`」と「同じ`kid`だが署名鍵が異なる」は、発生する例外が異なります。

- `kid`が見つからない：`JWKSNoMatchingKey`

- 鍵は選択できたが署名が一致しない：`JWSSignatureVerificationFailed`

テストでは両方を分けておくと、公開鍵のローテーション不備と改ざんを区別できます。

# `alg: none`は`UnsecuredJWT`で作る

`SignJWT`は署名付きJWTを作るAPIです。`alg: none`を指定して秘密鍵で`.sign()`しようとしても、正常な「署名なしJWT」にはなりません。

`alg: none`の拒否をテストする場合は、`UnsecuredJWT`で明示的に生成します。

```typescript
import { UnsecuredJWT } from 'jose'

export function issueUnsecuredIdToken(): string {
  const nowSec = Math.floor(Date.now() / 1000)

  return new UnsecuredJWT({ auth_time: nowSec })
    .setSubject('uid-1')
    .setIssuedAt(nowSec)
    .setIssuer(`https://securetoken.google.com/${TEST_PROJECT_ID}`)
    .setAudience(TEST_PROJECT_ID)
    .setExpirationTime(nowSec + 3600)
    .encode()
}
```

このトークンは`algorithms: ['RS256']`で拒否されます。ヘッダを先に確認している場合は、より具体的なアプリ独自エラーとして処理できます。

# キャッシュが効いていることを確認する

同じisolate内で2回検証しても、JWKS取得が1回だけであることを確認します。

```typescript
const fetchMock = await installJwksMock()
const token = await issueIdToken()

await verifyFirebaseIdToken(token, TEST_PROJECT_ID)
await verifyFirebaseIdToken(token, TEST_PROJECT_ID)

const jwksCalls = fetchMock.mock.calls.filter(([input]) => {
  const url = input instanceof Request ? input.url : String(input)
  return url === JWKS_URL
})

expect(jwksCalls).toHaveLength(1)
```

`String(call[0])`だけで比較すると、引数が`Request`だった場合に`[object Request]`となるため、モック側と同じ方法でURLを正規化しておきます。

# エラーの詳細は内部で保持し、外部には出し過ぎない

`jose`は失敗理由ごとに例外クラスを分けています。ログやテストでは、この情報を潰さない方が原因を追いやすくなります。

```typescript
import { errors } from 'jose'

function classifyJoseError(err: unknown): string {
  if (err instanceof errors.JWTExpired) {
    return 'token_expired'
  }
  if (err instanceof errors.JWSSignatureVerificationFailed) {
    return 'signature_verification_failed'
  }
  if (err instanceof errors.JWKSNoMatchingKey) {
    return 'no_matching_public_key'
  }
  if (err instanceof errors.JWTClaimValidationFailed) {
    return `invalid_claim:${err.claim}`
  }
  return 'unknown_token_error'
}
```

ただし、公開APIのレスポンスへ「署名鍵が一致しない」「`aud`が違う」などの詳細をそのまま返すと、攻撃者へ検証ルールを知らせることになります。

そのため、次のように分けました。

- クライアント：`401 unauthenticated`と安定したエラーコードを返す

- サーバーログ：`jose`の例外クラス・`code`・対象クレームを記録する

- テスト：例外クラスまたは内部エラーコードまで確認する

> 📝 「エラーを丸めない」は、**内部の原因情報を失わない**という意味です。利用者へ暗号検証の詳細をすべて公開する、という意味ではありません。

# 実装して分かったこと

- Firebase IDトークンの署名検証だけなら、サービスアカウントの秘密鍵は不要

- `jose`はCloudflare Workersを対応ランタイムとして明示しており、Web Crypto APIで完結する

- Firebase公式の検証要件には`exp`だけでなく`iat`と`auth_time`も含まれる

- Firebase公式が案内する公開鍵はX.509形式だが、GoogleのJWKエンドポイントを使うと`createLocalJWKSet()`へ渡しやすい

- `createRemoteJWKSet()`でも実装できるが、レスポンスの`max-age`へ厳密に合わせたい場合は自前キャッシュが扱いやすい

- JWTを丸ごとモックするより、テスト用鍵で実際に署名した方が`kid`や署名不一致まで確認できる

- `alg: none`は`SignJWT`ではなく`UnsecuredJWT`で作る

- 認証エラーの詳細はログでは保持し、クライアントへは必要以上に公開しない

# まとめ

Cloudflare WorkersでFirebase IDトークンを検証するだけであれば、Firebase Admin SDKを無理に持ち込まず、`jose`で署名とクレームを検証する構成はシンプルです。

特にテストでは、公開鍵取得だけをモックし、トークンはテスト用の秘密鍵で実際に署名すると、実装に近い経路を小さなテストで確認できます。

一方で、この方法はFirebase Authenticationの管理機能やトークン失効確認を置き換えるものではありません。必要な認証保証の範囲を先に決め、**署名検証だけなら****`jose`****、管理機能まで必要ならAdmin SDKやGoogle APIを含む構成**として分けるのが良さそうです。
