# 概要

Cloudflare Workers側でFirebase AuthenticationのIDトークンを検証する実装を行ったので、個人的な備忘録も兼ねてまとめました。

構成としては、Firebase AuthenticationでログインしたクライアントからIDトークンを受け取り、Workers側で署名とクレームを検証する形です。今回やりたかったのはFirebaseユーザーの作成・更新などではなく、**送られてきたIDトークンが正しいものか確認するだけ**です。

そのためFirebase Admin SDKは使わず、Workersでも利用しやすい `jose` を使って検証してみました。

https://www.npmjs.com/package/jose

# 今回やりたいこと

今回の実装で確認するのは以下になります。

- Googleの公開鍵に対応する秘密鍵で署名されていること
- 対象のFirebaseプロジェクト向けに発行されていること
- トークンの有効期限が切れていないこと
- Firebase UIDとして利用する `sub` が正しいこと

逆に以下は今回の対象外です。

- IDトークン発行後の失効確認
- Firebase Authentication上でユーザーが無効化・削除されていないかの確認
- Firebaseユーザーの作成・更新・削除

Firebase Admin SDKの `verifyIdToken()` も通常の呼び出しでは失効確認までは行いません。
今回はあくまで**IDトークンの署名とクレームを検証するところまで**をやっていきます。

# Firebase IDトークンを検証する

Firebase公式ドキュメントを見ると、サードパーティーのJWTライブラリで検証する場合は以下を確認する必要があります。

| 項目 | 確認内容 | 今回の実装 |
| --- | --- | --- |
| `alg` | `RS256` であること | `algorithms` |
| `kid` | 公開鍵セットに対応する鍵があること | `createLocalJWKSet()` |
| `exp` | 有効期限が未来であること | `jwtVerify()` |
| `iat` | 発行時刻が未来でないこと | 独自チェック |
| `aud` | FirebaseプロジェクトIDと一致すること | `audience` |
| `iss` | `https://securetoken.google.com/{projectId}` であること | `issuer` |
| `sub` | 空でないFirebase UIDであること | 独自チェック |
| `auth_time` | 認証時刻が未来でないこと | 独自チェック |

実装は👇のようになりました。

```typescript
import {
  createLocalJWKSet,
  decodeProtectedHeader,
  jwtVerify,
  type JWTPayload,
} from 'jose'

type FirebaseIdTokenPayload = JWTPayload & {
  auth_time?: number
  email?: string
  email_verified?: boolean
  firebase?: {
    sign_in_provider?: string
  }
}

const CLOCK_TOLERANCE_SEC = 30

export async function verifyFirebaseIdToken(
  token: string,
  projectId: string,
): Promise<FirebaseIdTokenPayload> {
  const header = decodeProtectedHeader(token)

  // セキュリティ上はjwtVerifyのalgorithms指定で拒否できる。
  // ここではログ・エラー分類を分かりやすくするため先に確認する。
  if (header.alg !== 'RS256') {
    throw new ApiError(
      401,
      'unauthenticated',
      `IDトークンのalgがRS256ではありません: ${header.alg ?? 'missing'}`,
    )
  }

  if (!header.kid) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンにkidがありません')
  }

  const keySet = await fetchJwks(Date.now())
  const { payload } = await jwtVerify<FirebaseIdTokenPayload>(
    token,
    createLocalJWKSet(keySet),
    {
      algorithms: ['RS256'],
      issuer: `https://securetoken.google.com/${projectId}`,
      audience: projectId,
      requiredClaims: ['exp', 'iat', 'sub', 'auth_time'],
      clockTolerance: CLOCK_TOLERANCE_SEC,
    },
  )

  const nowSec = Math.floor(Date.now() / 1000)

  if (!payload.sub) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのsubが空です')
  }

  if (payload.iat === undefined || payload.iat > nowSec + CLOCK_TOLERANCE_SEC) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのiatが不正です')
  }

  if (
    payload.auth_time === undefined ||
    payload.auth_time > nowSec + CLOCK_TOLERANCE_SEC
  ) {
    throw new ApiError(401, 'unauthenticated', 'IDトークンのauth_timeが不正です')
  }

  return payload
}
```

jwtVerify() に `issuer` と `audience` を渡しておくことで、署名に加えて `iss`、`aud`、`exp` などもまとめて検証できます。

`iat` と `auth_time` はFirebase側の要件に合わせて追加でチェックしています。
また `decodeProtectedHeader()` で取得した値は、この時点ではまだ未検証です。

今回はエラーを分かりやすくするために先に `alg` や `kid` を見ていますが、認可などの判断には必ず `jwtVerify()` を通した後の値を使います。

# 公開鍵を取得する

Firebase公式ドキュメントで案内されている公開鍵URLはX.509証明書を返します。

```text
https://www.googleapis.com/robot/v1/metadata/x509/securetoken@system.gserviceaccount.com
```

今回は `jose` の `createLocalJWKSet()` にそのまま渡したかったので、Googleが用意しているJWK形式のエンドポイントを使いました。

```typescript
const JWKS_URL =
  'https://www.googleapis.com/service_accounts/v1/metadata/jwk/' +
  'securetoken@system.gserviceaccount.com'
```

どちらも `securetoken@system.gserviceaccount.com` の公開鍵を取得するものですが、返ってくる形式が違うので少し注意が必要です。

# JWKSをキャッシュする

`jose` には `createRemoteJWKSet()` もあるので、普通に使うだけであればそちらでも良さそうです。
今回は以下をやりたかったので、自前で `fetch()` してキャッシュする形にしました。

- Googleの `Cache-Control: max-age` をそのままキャッシュ期限に使いたい
- テスト時にキャッシュを明示的に消したい
- 公開鍵取得時のエラー処理をアプリ側で揃えたい

実装は👇です。

```typescript
import type { JSONWebKeySet } from 'jose'

const DEFAULT_JWKS_TTL_MS = 10 * 60 * 1000

let jwksCache:
  | {
      keySet: JSONWebKeySet
      expiresAt: number
    }
  | undefined

export function clearJwksCache(): void {
  jwksCache = undefined
}

function parseMaxAgeMs(cacheControl: string | null): number | undefined {
  if (!cacheControl) return undefined

  const match = cacheControl.match(/(?:^|,)\s*max-age=(\d+)\s*(?:,|$)/i)
  if (!match) return undefined

  return Number(match[1]) * 1000
}

async function fetchJwks(now: number): Promise<JSONWebKeySet> {
  if (jwksCache && jwksCache.expiresAt > now) {
    return jwksCache.keySet
  }

  const res = await fetch(JWKS_URL)
  if (!res.ok) {
    throw new ApiError(
      503,
      'internal_error',
      'Firebase IDトークンの公開鍵を取得できませんでした',
      { status: res.status },
    )
  }

  const keySet = (await res.json()) as JSONWebKeySet
  if (!Array.isArray(keySet.keys) || keySet.keys.length === 0) {
    throw new ApiError(503, 'internal_error', '公開鍵セットが空です')
  }

  const maxAge =
    parseMaxAgeMs(res.headers.get('cache-control')) ?? DEFAULT_JWKS_TTL_MS

  jwksCache = {
    keySet,
    expiresAt: now + maxAge,
  }

  return keySet
}
```

キャッシュはモジュールスコープに置いているので、同じWorker isolateが使われている間だけ有効です。
永続的なキャッシュではありませんが、小規模なAPIであればまずはこのくらいでも十分かなと思います。
複数isolateで共有したくなったら、Cache APIやKVを検討する感じで良さそうです。

# テスト

認証周りなので、テストでは `verifyFirebaseIdToken()` 自体をモックせず、JWKSの取得部分だけをモックしました。
やっていることは以下です。

- `generateKeyPair('RS256')` でテスト用の鍵ペアを生成
- 公開鍵をJWKへ変換
- JWKSのレスポンスとして返す
- 秘密鍵でテスト用IDトークンを実際に署名
- 本番と同じ `jwtVerify()` で検証

```typescript
import { exportJWK, generateKeyPair, type JSONWebKeySet } from 'jose'
import { vi } from 'vitest'

const TEST_KID = 'test-key-1'

export async function installJwksMock(): Promise<ReturnType<typeof vi.fn>> {
  const { publicKey } = await getKeys()
  const jwk = {
    ...(await exportJWK(publicKey)),
    kid: TEST_KID,
    alg: 'RS256',
    use: 'sig',
  }

  const keySet: JSONWebKeySet = { keys: [jwk] }
  const fetchMock = vi.fn(async (input: RequestInfo | URL) => {
    const url = input instanceof Request ? input.url : String(input)

    if (url === JWKS_URL) {
      return Response.json(keySet, {
        headers: {
          'cache-control': 'public, max-age=3600',
        },
      })
    }

    throw new Error(`テストが想定していない外部fetch: ${url}`)
  })

  clearJwksCache()
  vi.stubGlobal('fetch', fetchMock)
  return fetchMock
}
```

`vi.stubGlobal()` で差し替えた `fetch` はテスト後に戻す必要があるので、キャッシュと合わせて `afterEach()` でクリアします。

```typescript
import { afterEach, vi } from 'vitest'

afterEach(() => {
  clearJwksCache()
  vi.unstubAllGlobals()
})
```

これでテスト順序に依存しづらくなります。

# 正常系・異常系のトークンを作る

テスト用IDトークンは `SignJWT` で生成しました。

```typescript
import { SignJWT } from 'jose'

type IdTokenOptions = {
  uid?: string
  kid?: string
  issuer?: string
  audience?: string
  issuedAt?: number
  authTime?: number
  expiresAt?: number
  signWithForeignKey?: boolean
}

export async function issueIdToken(
  options: IdTokenOptions = {},
): Promise<string> {
  const nowSec = Math.floor(Date.now() / 1000)
  const keys = options.signWithForeignKey
    ? await getForeignKeys()
    : await getKeys()

  return new SignJWT({
    auth_time: options.authTime ?? nowSec,
  })
    .setProtectedHeader({
      alg: 'RS256',
      kid: options.kid ?? TEST_KID,
    })
    .setSubject(options.uid ?? 'uid-1')
    .setIssuedAt(options.issuedAt ?? nowSec)
    .setIssuer(
      options.issuer ??
        `https://securetoken.google.com/${TEST_PROJECT_ID}`,
    )
    .setAudience(options.audience ?? TEST_PROJECT_ID)
    .setExpirationTime(options.expiresAt ?? nowSec + 3600)
    .sign(keys.privateKey)
}
```

これで以下のパターンを作れます。

- 期限切れの `exp`
- 未来の `iat`
- 未来の `auth_time`
- 別プロジェクトの `aud`
- 不正な `iss`
- 空の `sub`
- JWKSに存在しない `kid`
- JWKSとは別の秘密鍵で署名したトークン

`kid` が見つからない場合は `JWKSNoMatchingKey`、鍵は見つかったけど署名が違う場合は `JWSSignatureVerificationFailed` になるので、テストでは分けておくと原因を追いやすいです。

# `alg: none` も確認する

`alg: none` のテストも入れました。ここは `SignJWT` ではなく `UnsecuredJWT` を使います。

```typescript
import { UnsecuredJWT } from 'jose'

export function issueUnsecuredIdToken(): string {
  const nowSec = Math.floor(Date.now() / 1000)

  return new UnsecuredJWT({ auth_time: nowSec })
    .setSubject('uid-1')
    .setIssuedAt(nowSec)
    .setIssuer(`https://securetoken.google.com/${TEST_PROJECT_ID}`)
    .setAudience(TEST_PROJECT_ID)
    .setExpirationTime(nowSec + 3600)
    .encode()
}
```

このトークンは `algorithms: ['RS256']` で拒否されます。

# キャッシュのテスト

同じisolate内で2回検証した場合に、JWKSの取得が1回だけになることも確認します。

```typescript
const fetchMock = await installJwksMock()
const token = await issueIdToken()

await verifyFirebaseIdToken(token, TEST_PROJECT_ID)
await verifyFirebaseIdToken(token, TEST_PROJECT_ID)

const jwksCalls = fetchMock.mock.calls.filter(([input]) => {
  const url = input instanceof Request ? input.url : String(input)
  return url === JWKS_URL
})

expect(jwksCalls).toHaveLength(1)
```

`fetch` の引数が `Request` の場合もあるので、URLを比較するときは `String(call[0])` だけで済ませず、`Request` なら `.url` を見るようにしています。

# エラーは内部で詳しく持つ

`jose` はエラー内容ごとに例外クラスが分かれているので、ログやテストでは情報を残しておくと調査しやすいです。

```typescript
import { errors } from 'jose'

function classifyJoseError(err: unknown): string {
  if (err instanceof errors.JWTExpired) {
    return 'token_expired'
  }
  if (err instanceof errors.JWSSignatureVerificationFailed) {
    return 'signature_verification_failed'
  }
  if (err instanceof errors.JWKSNoMatchingKey) {
    return 'no_matching_public_key'
  }
  if (err instanceof errors.JWTClaimValidationFailed) {
    return `invalid_claim:${err.claim}`
  }
  return 'unknown_token_error'
}
```

ただし、この詳細をそのままAPIレスポンスで返す必要はないかなと思います。

今回は以下のように分けました。

- クライアントには `401 unauthenticated` と安定したエラーコードを返す
- サーバーログには `jose` の例外クラスや対象クレームを残す
- テストでは例外クラスや内部エラーコードまで確認する

外向けにはシンプルに、内部では原因を追える状態にしておく感じです。

# 実装して分かったこと

今回試してみて分かったことをまとめると👇になります。

- Firebase IDトークンの署名検証だけならサービスアカウントの秘密鍵は不要
- `jose` を使うとWorkers上でもJWT検証をシンプルに書ける
- `exp` だけではなく `iat` や `auth_time` も確認する
- Firebase公式が案内している公開鍵はX.509形式
- JWK形式のGoogleエンドポイントを使うと `createLocalJWKSet()` に渡しやすい
- `createRemoteJWKSet()` でも実装できる
- キャッシュ期限をGoogleの `max-age` に合わせたい場合は自前管理もしやすい
- JWT自体をモックするより、実際にテスト用鍵で署名した方が異常系まで確認しやすい
- `alg: none` は `UnsecuredJWT` で作る
- 認証エラーの詳細はログ側に残して、クライアントへは出し過ぎない

# まとめ

Cloudflare WorkersでFirebase IDトークンの検証だけを行いたい場合、Firebase Admin SDKを使わず `jose` で署名とクレームを確認する形でもシンプルに実装できました。

特にテストでは、JWKSだけモックしてトークン自体は実際に署名する形にすると、`kid` や署名不一致なども含めて確認できるので良かったです。

もちろんFirebaseユーザーの管理やトークン失効確認まで必要な場合は別の構成が必要になります。

今回のように「IDトークンが正しいか確認してUIDを取得したい」くらいの用途であれば、選択肢の1つとして参考になればと思います。
